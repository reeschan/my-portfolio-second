## 2. 検索エンジニアリング（OpenSearch / 日本語検索）

最も密度の高い領域。日本語形態素解析と同義語運用の制約を踏まえた設計ができる。

### 日本語解析・辞書運用 【実務】
- AWS OpenSearch Service上でSudachi / kuromojiのアナライザを併用した商品インデックスの設計・運用
- Sudachiユーザー辞書とシノニム辞書の取り込みタスク設計
  - S3 → Packages API（Create / Update / AssociatePackage）→ 再インデックス → エイリアス切り替えのフロー
  - ユーザー辞書のビルドはJava / Python実装しかないため、GitHub ActionsでSudachiPyを使ってビルドする構成
- 同義語運用の制約を把握
  - Sudachi同義語辞書（CSV形式）とOpenSearch synonym filter（Solr形式）の違い
  - AWSマネージド環境ではChikkarプラグインが使えないこと
  - トークナイザとの分割不一致に備えた `lenient: true` の必要性
  - `updateable: true` はsearch analyzer限定で、ホットリロードするにはindex / search analyzerの分離が必要なこと
  - 検索時のみに同義語展開するとIDF・スコアが変わるため、回帰テストが必要なこと
  - ユーザー辞書の更新はBlue/Greenデプロイのタイミングに依存すること

### 検索品質改善 【実務・設計】
- 商品バリアントのグルーピング：`collapse` + `inner_hits` による集約
  - 単体商品にも自身のIDをグループIDとして持たせ、クエリを一本化してページネーション崩れを回避
- ゼロヒットクエリ分析を起点としたシノニム候補の自動抽出パイプラインを構想・推進
  - 検索ログ（BigQuery）、embedding類似度、LLM判定を組み合わせ、人間レビューを経て辞書に反映する流れ
- LLMによるシノニム候補生成と、その評価方法の設計（後述）
- セグメントレプリケーション / リモートストア構成のインデックス設定の読解・改修

### ベクトル検索 【調査・設計】
- OpenSearch k-NN（HNSW）とBM25のハイブリッド検索、rescore
- Milvusを使った類似検索の初期リリース計画（データ不足時の段階的アプローチ、Precision@K / NDCGによる評価）

## 3. LLM・AI連携

### embedding・分類 【実務】
- 約1,500万件の商品データを対象にした類似推定・分類処理（フリーランスとして初のembedding案件）
- OpenAI Embeddings / Bedrock Titan / transformers.js（ローカル実行）をコストと運用面で比較
- 約200色ラベルへの分類で、embedding類似度とLLM直接分類をコスト試算込みで比較し、解釈性と実装の単純さからLLM分類を選択。Batch APIによる約50%のコスト削減も検討

### プロンプト管理と評価 【実務・設計】
- TypeScriptで散在していたプロンプトを、バージョン管理する構成へ整理
  - 型付き定義、zodによる出力検証、共通invoker、環境変数でのバージョン切り替え、Vitestスナップショット
- 評価ツールの比較：Braintrust / Evalite / Promptfoo / LangSmith / Langfuse / DeepEval
  - クライアントデータを外部SaaSへ送れるかどうか、TypeScript対応、コストの観点で選定
- 「評価データセット、特に負例のラベリングが最大のボトルネック」という認識のもと、決定論的チェック、LLM-as-a-judge、人間のサンプリングを組み合わせる評価設計
- LangChainは課題に対して抽象化コストが見合わないと判断し、SDKを直接使う構成を選択

### AIアプリケーション基盤 【実務・調査】
- 静的サイト（React SSG）からLLMを安全に呼ぶ構成
  - Lambda Function URL + Hono + AI SDKでストリーミング応答を実現（API Gatewayはバッファリングでストリーミング不可のため除外）
  - Cognitoのアクセストークンを `aws-jwt-verify` で検証
- 画像解析：Few-shot、Fine-tuning、RAG、専用CVモデルの使い分けを整理
- マネージドRAG（Gemini File Search、OpenAI File Search / Responses API、Bedrock Knowledge Bases）の比較
- RAGの処理フロー設計（2025年〜）

## 4. クラウド・アーキテクチャ（AWS）

### バッチ・スケジューリング 【実務・設計】
- キャンペーン開始・終了に連動した商品フィーダーのECSタスク起動設計
  - EventBridge Scheduler / Step Functions / Lambda Durable Functions / DynamoDB TTL + Streams / SQS遅延配信を、精度・経路・運用コストで比較
- ECSバッチタスクの監視設計：CloudWatchカスタムメトリクスで起動、ハートビート、処理件数サマリーを監視
- ECS Managed Daemons（2026年GA）、FireLens、Container Insights、ADOTの使い分けを理解

### 認証・認可 【設計】
- マイクロサービス間の共通認証・認可基盤の設計
  - 独立した認証サーバーによる内部トークン発行と、各サービスでのJWKSローカル検証
  - KMS非対称鍵での署名、`kid` によるローテーション
  - Cognitoユーザーとゲスト（パスワード通過）を一つの内部トークンに正規化。パスワード通過はcapabilityとして扱う
- 認可方式の比較
  - JWTに権限を載せる方式：プライベートフォルダ要件で不可と判断
  - JWTに属性のみを載せる方式
  - OpenFGA（ReBAC）
  - Amazon Verified Permissions / Cedar：トークン発行不可、逆引き不可のため不採用
- 「認可判定を `can(principal, action, resource)` の共有ライブラリに閉じ込める」ことを初日からの制約とし、後から内部実装を差し替えられる設計にした
- Transaction Tokens、Token Exchange、Phantom Token、SPIFFE等の最新動向も把握

### その他 【実務】
- Elastic Beanstalk + GitHub Actionsのデプロイパイプライン（Slack通知付き）のトラブル対応
- ALB / EC2のセキュリティグループ設計
- モック画面からのOpenAPI（Swagger）仕様の起こし
- フェデレーションユーザーとIAMロールの権限関係（SageMakerアクセス）

## 8. 仕事の進め方・人柄（会話から客観的に読み取れる傾向）

### 根拠を確認する
AIや資料の説明を鵜呑みにせず、出典を求めたり実物で反証したりする場面が繰り返し見られた。
- Chikkarプラグインが存在しないという説明に出典を求め、訂正につながった
- ユーザー辞書の更新には必ず再インデックスが必要という説明の正確さを問い、ホットリロードの適用範囲というニュアンスを引き出した
- VRoidの虹彩テクスチャについての誤った説明を、実際のエクスポート結果を示して訂正した

### 単純さと運用性を優先する
- embeddingより解釈しやすいLLM分類を選んだ
- LangChainを入れない判断をした
- 単体商品にもグループIDを持たせてクエリを一本化した

いずれも「動く」だけでなく、後から読む人や運用が回るかどうかを基準にしている。S3バケット名やタスク名の命名にも、後から見た人に伝わるかを気にかけている。

### コスト感覚がある
- APIの単価、Batch APIの割引、シート課金の仕組みまで確認してから選定する
- クライアントデータを外部サービスへ送信することのリスクにも意識が向いている

### スコープを超えて提案する
- PoC案件では、求められた範囲の実装にとどまらず、エンドクライアントにとって有益な検討事項を自発的に提案している
- 長期的な信頼関係の構築を意図した動き方である

### 自走してキャッチアップする
- 独立後、React Native、OpenSearch、AWSインフラ、LLM連携へと、案件に先回りする形で技術範囲を自力で広げてきた
- 新機能（ECS Managed Daemons、Claude Codeの最新機能など）を公開当日に確認するような習慣がある

### 言語化と整理を重視する
- 契約の区切りを、ポートフォリオと知見の棚卸しに充てる判断をした
- 設計ドキュメント（認証基盤、VRMワークフロー、辞書運用）を成果物として残す傾向がある

### 自分の考えを絶対視しない
- 「自分の考えは常に100%に満たない」という前提を持ち、他者の意見も同様に不完全なものとして検討する
- 失敗から学んで是正してきた経験を自覚している

### 構造的に考える
- 日本史・地政学などへの関心がある
- 物事を構造・システムとして捉える思考を好む

### その他
- 議論は分析的で、前提が曖昧なときは遠慮なく指摘する
- 一方で、雑談ではユーモアを交えた軽いやり取りも好む
