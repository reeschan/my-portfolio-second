# 0010. PBI 駆動の開発: PBI・WORK・ADR を先に書いてから実装する

- 状態: 採用
- 日付: 2026-10-06
- 関連: PBI-0001、[docs/agents/development-flow.md](../agents/development-flow.md)

## 背景

改修を複数のエージェントに任せるようになり、次のことが起きやすくなった。

- 依頼の解釈がエージェントごとにずれ、「何をもって完了か」が曖昧なまま実装が始まる
- 途中の判断 (なぜこの方法にしたか、何を見送ったか) が会話の中に消え、次の作業者が辿れない
- 設計判断が ADR にならず、同じ議論を繰り返す

## 決定

1. ベースの実装は **PBI を起こしてから**着手する。PBI には受け入れ条件と、それを確かめるテストを書く
2. 作業の計画と記録は **WORK** に残す。PBI と同じフォルダ (`docs/pbi/<番号>-<slug>/`) に置く
3. 戻すのにコストがかかる判断は **ADR** に残し、PBI からリンクする (いつ書くかは development-flow.md)
4. 手順の正本は `docs/agents/development-flow.md`。Self 組織の共通スキル `start-pbi` / `create-pr` がそれを読む
5. 小さな修正 (誤字、テストだけの巡回など) は PBI を不要とする

## 検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| リポジトリ内の Markdown で PBI/WORK (採用) | エージェントがそのまま読み書きできる。PR の差分で一緒にレビューできる | 一覧性は Issue 管理ツールに劣る |
| GitHub Issues / Projects | 一覧・担当・期日の管理ができる | エージェントの作業記録を残す場所としては粒度が合わず、オフラインで読めない |
| 何も決めない | 手間がない | 上の問題が続く |

## 結果

- PR のレビューは「PBI の受け入れ条件を満たしているか」を基準にできる
- PBI の一覧 (`docs/pbi/README.md`) は手で更新する。必要になれば Issues と連携する
