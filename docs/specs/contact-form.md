# お問い合わせフォーム

- 日付: 2026-10-13
- 状態: 合意済み (design-flow の grilling で持ち主と確認)
- 用語: [CONTEXT.md](../../CONTEXT.md) の「お問い合わせ」「送り主」「持ち主」

## Problem Statement

このサイトを見た採用担当や発注者が、持ち主に連絡したくなっても、サイトの中に連絡の手段が無い。AI チャットは経歴について答えるだけで、持ち主に用件は届かない。
かといって、持ち主のメールアドレスをページに載せると、アドレスを集める bot に拾われてスパムが届くようになる。持ち主は、アドレスを公開せずに、閲覧者からの連絡を確実に受け取りたい。

## Solution

サイトに「お問い合わせ」のタブ (`/contact`) を足す。送り主は名前・メールアドレス・本文を書いて送る。お問い合わせは、持ち主がふだん通知を受けている Slack のチャンネルに届き、持ち主は通知に載った送り主のメールアドレスへ手で返信する。
サイトはメールを送らず、送り主への自動返信もしない。連打や bot を抑えるために、既存の IP ごとのレート制限を共通化してフォームにも掛け、人には見えない入力欄 (ハニーポット) で bot をふるい落とす。届けられなかったときは送り主にそう伝え、入力を消さずに送り直せるようにする。

## User Stories

1. 送り主として、タブから「お問い合わせ」を開きたい。サイトのどこからでも連絡の手段にたどり着けるようにするため
2. 送り主として、名前・メールアドレス・本文の 3 つだけを書いて送りたい。手間をかけずに連絡できるようにするため
3. 送り主として、必須の項目が空のまま送ろうとしたら、どこが足りないかを知りたい。直してから送れるようにするため
4. 送り主として、メールアドレスの形が正しくないときに知らされたい。返信が届かない事態を避けるため
5. 送り主として、本文が短すぎる (10 字未満) ときや長すぎる (2000 字超) ときに知らされたい。送れる長さに収めるため
6. 送り主として、入力した情報が何に使われるかを送る前に知りたい。安心して送れるようにするため
7. 送り主として、送ったあとに「受け付けました」と表示されたい。届いたことが分かるようにするため
8. 送り主として、送ったあとにもう一通送りたいときは、フォームに戻りたい。別の用件も連絡できるようにするため
9. 送り主として、送れなかったときにはそう表示され、入力した内容が残っていてほしい。書き直さずに送り直せるようにするため
10. 送り主として、短い時間に何度も送ったときに、しばらく待つよう知らされたい。なぜ送れないのかが分かるようにするため
11. 送り主として、お問い合わせを受け付けられない状態のときは、送った時点でそう知らされたい。届いたと誤解しないようにするため
12. 英語で閲覧している送り主として、フォームの見出し・項目名・案内・エラーを英語で読みたい。日本語が読めなくても連絡できるようにするため
13. キーボードだけで操作する送り主として、Tab と Enter だけで入力から送信までできるようにしたい
14. スクリーンリーダーを使う送り主として、各項目の名前とエラーを読み上げてほしい
15. 送信中の送り主として、二重に送らないよう、送信中であることが分かり、送信のボタンが押せなくなっていてほしい
16. 持ち主として、お問い合わせが Slack のいつものチャンネルに届いてほしい。サイトの通知をひとつの場所で見るため
17. 持ち主として、通知に送り主の名前・メールアドレス・本文の全文・受け付けた日時が載っていてほしい。サイトを見に行かずに返信できるようにするため
18. 持ち主として、通知の本文に書かれた `<!channel>` やリンクの書式が効かず、ただの文字として出てほしい。送り主にチャンネルを荒らされないようにするため
19. 持ち主として、通知に送り主の IP アドレスが載らないでほしい。必要以上に個人を特定できる情報を持たないため
20. 持ち主として、自分のメールアドレスがページにもリポジトリにも出ないでほしい。スパムの宛先にされないようにするため
21. 持ち主として、サイトが送り主に自動でメールを返さないでほしい。他人のアドレスにメールを送る踏み台にされたり、ドメインの評判が落ちたりしないようにするため
22. 持ち主として、同じ IP からの送信が 1 時間に 5 回を超えたら断ってほしい。連打で Slack が埋もれないようにするため
23. 持ち主として、bot が隠れた入力欄を埋めて送ってきたものは、通知せずに捨ててほしい。そのうえで bot には成功したように見せ、手口を変えるきっかけを与えたくない
24. 持ち主として、Slack に届けられなかったお問い合わせを「受け付けた」と表示しないでほしい。送り主に送り直してもらうため
25. 持ち主として、お問い合わせをサイトのどこにも保存しないでほしい。個人情報を持つ場所を増やさないため
26. 持ち主として、チャットのレート制限とお問い合わせのレート制限を別々に数えてほしい。チャットをたくさん使った人が問い合わせできなくなる、あるいはその逆が起きないようにするため

## Implementation Decisions

- **ページ**: `/contact` を足し、タブの並びは「チャット」と「テーマ」のあいだにする。タブの表示名と、ページの文言 (見出し・項目名・案内・注意書き・エラー・完了の表示) は、日本語と英語の辞書に持つ。ページは他のページと同じ枠 (タブと本文のパネル) に入れる
- **フォームの部品**: features の層に、お問い合わせのフォームの部品を足す。状態は「入力中」「送信中」「受付済み」の 3 つ。受付済みでは、フォームの代わりに受付の案内と「別のお問い合わせを送る」ボタンを出し、押すと空のフォームに戻る。送信に失敗したら入力中に戻り、入力はそのまま残してエラーを出す。API は既存の `apiFetch` を通して呼ぶ (直接 `fetch` を書かない)
- **注意書き**: フォームの下に「いただいた情報は返信のためだけに使い、第三者には渡しません」(英語版も) を出す
- **入力の決まり** (画面と API の両方で同じスキーマを使う):
  - 名前: 必須、前後の空白を除いて 1〜100 字
  - メールアドレス: 必須、254 字まで、メールアドレスの形式
  - 本文: 必須、前後の空白を除いて 10〜2000 字
  - ハニーポット: 人には見えない入力欄を 1 つ置く (読み上げとタブ移動からも外す)。API は値を受け取るが、空であることだけを見る
- **API `POST /api/contact`** (JSON を受け取る):
  - `withErrorHandling` で包む (他の API と同じ)。`withBearerAuth` は付けない (誰でも送れる)
  - 処理の順: 通知先の設定を確かめる → IP ごとのレート制限 → 本文の検証 → ハニーポットの判定 → Slack へ送信
  - `SLACK_WEBHOOK_URL` が無ければ 503 (「現在お問い合わせを受け付けられません」)。送ったつもりで誰にも届かない状態を作らないため
  - 同じ IP から 1 時間に 5 回を超えたら 429。IP は既存のチャットと同じく `x-forwarded-for` の先頭から取る
  - 形式が正しくなければ 400
  - ハニーポットが埋まっていれば、Slack に送らずに受付と同じ成功の応答を返す
  - Slack に送れたら 200 (受付済み)。送れなかったら 502 (「送信に失敗しました。時間をおいてもう一度お試しください」)
  - 応答の本文の形は他の API (`/api/chat`・`/api/now`) の成功とエラーの形に合わせる
- **Slack への通知**: 既存の `withSlackNotify` (応答を返したあとに、失敗しても構わない前提で送るデコレータ、ADR 0018) は使わない。お問い合わせでは Slack が唯一の届け先なので、既存の `notifySlack` を応答の前に直接呼び、結果 (送れたか) で応答を決める。送り先は全体で共通の `SLACK_WEBHOOK_URL` (お問い合わせ専用の Webhook は作らない)。中身は、見出し・名前・メールアドレス・本文の全文・受け付けた日時。送り主が書いた文字列はすべて既存の `escapeSlackText` で無害化する。IP アドレスは載せない。中身の組み立ては、他の機能の通知 (チャット・/now) と同じく、機能ごとの通知の部品に置く
- **レート制限の共通化**: チャットの IP ごとのレート制限 (サーバーのメモリに時刻を持つ簡易な仕組み) を共通の場所に移す。呼び出し側が「数える枠の名前・時間の幅・上限の回数」を渡せる形にして、チャット (10 分 20 回) とお問い合わせ (1 時間 5 回) を別々に数える。チャットの振る舞いは変えない。インスタンスをまたいでは数えられない (目安の制限である) ことは今までどおり受け入れる
- **持ち主のメールアドレス**: ページ・辞書・コード・設定ファイル・ドキュメントのどこにも書かない
- **ADR**: 「お問い合わせの届け先は Slack だけにし、応答の前に送って結果を確かめる (ADR 0018 の後から送る通知とは分ける)。メールの送信と自動返信はしない」を新しい ADR に残す。あわせて、`testing/e2e-policy.yml` の外部モック観点の対象に `/contact` と `/api/contact` を足すことも、この ADR に書く

## Testing Decisions

- **良いテスト**: 外から見える振る舞い (HTTP のステータスと応答、Slack に送られた中身、画面に出るもの) だけを確かめる。内部の関数の呼ばれ方や状態の持ち方には依存しない。本物の Slack は呼ばない
- **合意済みの seam**:
  1. **API `POST /api/contact` を直接呼ぶユニットテスト (Vitest)**。Slack の Webhook への `fetch` をモックする。確かめること: 正しい入力で 200 が返り、Slack に 1 回送られ、その中身に名前・メールアドレス・本文があり、IP アドレスが無く、`<!channel>` などが無害化されている / 必須の欠け・形式の誤り・長さの超過で 400、Slack に送られない / ハニーポットが埋まっていると成功の応答を返し、Slack に送られない / 同じ IP の 6 回目が 429 になり、別の IP は通る / Slack が失敗すると 502 / `SLACK_WEBHOOK_URL` が無いと 503
  2. **`/contact` ページの E2E (Playwright)**。`page.route` で `/api/contact` をモックする。確かめること: 送ると受付の案内が出て、「別のお問い合わせを送る」で空のフォームに戻る / API が 502 や 429 を返すとエラーが出て、入力が残っている / 必須の欠けやメールアドレスの形式の誤りで送れず、どこが悪いかが出る / 英語に切り替えると文言が英語になる / キーボードだけで送れる / アクセシビリティ (axe) の重大な違反が無い / タブの並びに「お問い合わせ」が「チャット」と「テーマ」のあいだに出る / ページのどこにも持ち主のメールアドレスが無い
- **共通化したレート制限**: 既存のレート制限のユニットテストを移し、「枠の名前ごとに別々に数える」「枠ごとの時間の幅と上限が効く」を足す
- **お手本**: API はチャットの route のテスト (`fetch` のモック、IP を変えたリクエストの作り方、`after` の差し替え)。E2E はチャットの E2E (`page.route` で API をモックする) と、`e2e/fixtures.ts` のページ一覧 (smoke・a11y・タブの並びのテストが自動で新しいページを含める)。Slack の中身の確かめ方は `/now` とチャットの通知のテスト
- **観点の対応**: API は api-contract (必須) と external-mock、ページは smoke (必須)・content・interaction・a11y・external-mock。`pnpm test:coverage-map -- --check` で必須の観点に穴が無いことを確かめる

## Out of Scope

- メールの送信 (持ち主への通知メール、送り主への受付確認メール・自動返信)
- お問い合わせの保存・一覧・管理画面
- 添付ファイル、種別の選択、会社名などの項目
- CAPTCHA (Cloudflare Turnstile など) や外部のスパム判定サービス
- インスタンスをまたいで確実に数えるレート制限 (Upstash Redis で数えるなど)。足りなくなったら別の PBI で上げる
- お問い合わせ専用の Slack のチャンネル・Webhook
- 持ち主のメールアドレスの掲載

## Further Notes

- 持ち主が最初に挙げたメールアドレスは、通知を Slack だけにしたので使わない。ページにもリポジトリにも書かない (持ち主の強い要望)
- 本番で `SLACK_WEBHOOK_URL` が設定されていることは、既存の /now とチャットの通知で前提になっている。E2E は `SLACK_WEBHOOK_URL` を空にして起動するので、ページの E2E は API をモックする
- レート制限はメモリ内の目安なので、Vercel のインスタンスが分かれると上限より多く通ることがある。Slack が荒れるようなら、Upstash Redis で数える形に上げる
- PBI は 0018、ADR は 0028 が空いている (2026-10-13 時点。採番の前に全ブランチを確かめる)
