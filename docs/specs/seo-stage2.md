## Problem Statement

持ち主は、採用担当や発注者が検索からこのサイトにたどり着き、経歴や作品の中身まで検索エンジンに正しく理解されることを望んでいる。1 段目 (PBI-0019・0020・0023) で title・canonical・sitemap・RSS・記事の BlogPosting は入ったが、まだ次の問題が残っている。

- 持ち主が誰で何をする人かを表す構造化データ (Person・WebSite) が無く、記事の BlogPosting には画像と発行者が無い。
- 存在しない URL では Next.js の既定の英語の 404 が出て、タブも導線も無く、閲覧者がサイトの中に戻れない。しかもトップの canonical と説明文を受け継いでいる。
- 各ページの description が短く (例:「制作したもの」)、検索結果の説明文として役に立たない。
- /now の記事は、本文の先頭の見出しが記事の題と同じとき、同じ文の見出しが二重に出て、説明文も題の繰り返しから始まる。本文が `##` から始まると、h1 の次がすぐ h3 になって段が飛ぶ。
- 背景のテーマを選ぶだけのページ (/theme) が索引の対象になっている。
- こうした退行を機械的に止める仕組みが無い。

本番では正のホストと転送の向きが逆になっている (canonical は apex、配信は www に転送)。これは PBI-0027 が直すので、この仕様の範囲ではない。ただし、外部の監査道具 (jev-seo) は、この食い違いがあるあいだは、ページ単位の検査をほぼすべて飛ばす。

## Solution

jev-seo を道具として丸ごと入れるのではなく、その 52 本の検査のうちこのサイトに効くものの考え方を借りて、サイトのコードを直し、同じ観点を自前のテストに写す。

- 持ち主を表す Person と、サイトを表す WebSite を全ページに出し、/overview を ProfilePage にする。記事の BlogPosting に画像と発行者を足し、記事のページに「トップ › Now › 記事」の BreadcrumbList を出す。
- サイトの見た目の 404 ページを作り、迷い込んだ閲覧者をトップ・/now・/works に戻す。
- 各ページの description を、検索結果で読める長さ (50〜120 文字) に書き直す。
- 記事の見出しを、題との二重を落とし、段を詰めて描く。
- 道具のページ (/theme) を索引から外す。
- 最低限のセキュリティヘッダーを付ける。
- 「seo」のテスト観点を新しく作り、全ページで SEO の基本が崩れていないかを確かめる。
- PBI-0027 とこの段が本番に出たあと、持ち主が手元で jev-seo を 1 回だけ当てて監査し、所見を次の段の材料にする。

## User Stories

1. 採用担当として、持ち主の名前や「フルスタックデベロッパー」で検索したときに、このサイトが持ち主本人のものとして出てほしい。本人のポートフォリオだと迷わず分かるようにするため
2. 採用担当として、検索結果の説明文を読んで、そのページに何があるか (経歴・スキル・作品など) を開く前に知りたい。見るべきページを選べるようにするため
3. 検索エンジンとして、このサイトの持ち主を Person として読み取り、GitHub と LinkedIn のアカウントと結び付けたい。人物の情報を正しく関連付けるため
4. 検索エンジンとして、サイトを WebSite として、/overview を持ち主の ProfilePage として読み取りたい。サイトの構造を理解するため
5. 検索エンジンとして、1 つのページの中で同じ人物が別々のものとして書かれていないでほしい。著者・発行者・サイトの持ち主を同じ人物として理解するため
6. 検索エンジンとして、/now の記事の BlogPosting に画像・著者・発行者があってほしい。記事を検索結果で目立たせる条件を満たすため
7. 検索エンジンとして、記事のページの階層 (トップ › Now › 記事) を BreadcrumbList で読み取りたい。検索結果にパンくずを出すため
8. SNS で共有する人として、どのページを共有しても、カードの画像が正しく出てほしい。共有されたリンクが見栄えよく伝わるため
9. SNS で共有する人として、カードの言語が、ページの表示言語と合っていてほしい。表示のずれを避けるため
10. 閲覧者として、存在しない URL を開いたときに、サイトの見た目のまま「ページが見つかりません」と日本語で知らされたい。サイトの中で迷子にならないようにするため
11. 閲覧者として、知らない id の記事の URL を開いたときも、同じ 404 のページが出てほしい。記事が消えたのか URL が違うのかで迷わないため
12. 閲覧者として、404 のページからトップ・Now・Works に移りたい。探していたものにたどり着き直すため
13. 英語で閲覧している人として、404 のページの文言を英語で読みたい。日本語が読めなくても次の行き先が分かるようにするため
14. 検索エンジンとして、404 のページを正のページと取り違えないよう、404 には canonical も共有の URL も無く、ステータスが 404 であってほしい。誤って索引に載せないため
15. /now の記事の読者として、記事の題と同じ見出しが本文の先頭で繰り返されないでほしい。読みやすくするため
16. /now の記事の読者として、記事の見出しが段を飛ばさずに並んでいてほしい。支援技術でも構造をたどれるようにするため
17. 検索エンジンとして、記事の説明文が題の繰り返しではなく本文の中身から始まってほしい。記事の内容を正しく要約するため
18. RSS の購読者と /now の一覧の閲覧者として、記事の抜粋が題の繰り返しから始まらないでほしい。中身をすぐ読めるようにするため
19. 検索エンジンとして、背景のテーマを選ぶだけのページ (/theme) は索引に載せなくてよいと知りたい。中身の薄いページで評価を下げないため
20. 持ち主として、/chat は「経歴に答える AI」として索引に残ってほしい。サイトの売りの 1 つを検索から見つけてもらうため
21. 閲覧者として、どのページの見出しも段を飛ばさずに並んでいてほしい。支援技術でも構造をたどれるようにするため
22. 検索エンジンとして、各ページの h1 が 1 つで、ページの主題を表していてほしい。主題を取り違えないため
23. 持ち主として、サイトが他のサイトの枠の中に埋め込まれないでほしい。なりすましやクリックの乗っ取りに使われないようにするため
24. 持ち主として、ブラウザがファイルの種類を推測せず、リンク元の情報を必要以上に渡さないでほしい。基本的な安全の水準を満たすため
25. 持ち主として、description の文言を自分で確かめてから公開したい。経歴の言い回しを自分の言葉にするため
26. 持ち主として、ページを足したり文言を変えたりしたときに、SEO の基本 (title・description・canonical・h1・見出し・構造化データ) が崩れたら、テストで気付きたい。知らないうちに評価を下げないため
27. 持ち主として、ページを足したら、そのページも自動で SEO の検査の対象になってほしい。検査の漏れを作らないため
28. 持ち主として、sitemap に載る URL が開けることを確かめたい。存在しない URL を検索エンジンに知らせないため
29. 持ち主として、本番に出たあとに jev-seo を手元で 1 回当て、サイトの外から見た監査の結果を得たい。テストに写していない観点の穴を見つけるため
30. 持ち主として、監査ではページの本文を外部の判定 (Jev) に送ってよいが、送るのは公開ページの本文だけにしたい。秘密の資料を外に出さないため
31. 持ち主として、監査の出力がリポジトリに紛れ込まないでほしい。生成物をコミットしてしまわないため
32. 持ち主として、監査の手順を後から読んで同じように回せるようにしたい。次の段でもう一度当てられるようにするため

## Implementation Decisions

### 構造化データ

- 構造化データを組み立てる関数は、記事用 (1 段目で作ったもの) と同じ置き場所に足し、同じ書き出しの関数 (`<` をエスケープするもの) を使う。
- ルートのレイアウトが WebSite と Person を 1 つの `<script type="application/ld+json">` に `@graph` で出し、ページの種類ごとの部分 (ProfilePage・BlogPosting・BreadcrumbList) は、ページが別の script で出して `@id` で指す。App Router ではレイアウトにページの中身を渡せないため、script は最大 2 つになるが、Person は 1 ページに 1 つだけになる (実装の段で読み替えた。PBI-0028 の WORK)。テストは、ページのすべての ld+json を集めて型で探す。
- Person と WebSite は、ルートのレイアウトで全ページ (トップ・404・/theme を含む) に出す。トップはタブ付きの枠を使っていないので、タブ付きの枠ではなくルートのレイアウトに置く。
- Person: 名前・職種 (「フルスタックデベロッパー」)・アカウント (sameAs に GitHub と LinkedIn)・画像 (アバター) は、持ち主のプロフィールの表示データ (日本語) から取り、表示言語によらず同じ値を出す。英語版は索引に載せないので、言語で人物の情報を変えない。記事の著者名の定数も、同じ表示データから取る形にそろえ、二重に持たない。X のアカウントは無いので、twitter:site も出さない。
- WebSite: サイト名と正のホストの URL。publisher は Person を指す。
- Person・WebSite には `@id` (正のホストの URL に `#person`・`#website` を付けたもの) を持たせ、ほかの部分からはこの `@id` で指す。記事の BlogPosting の author と publisher、ProfilePage の mainEntity は、Person を `@id` で指す。1 ページに Person は 1 つしか出ない。
- ProfilePage: /overview でだけ出す。
- BlogPosting: 画像と発行者を足す。画像は、PBI-0024 (記事の画像) の記事ごとの画像があればそれ、無ければサイトの OG 画像を使う。BlogPosting の変更は PBI-0024 のマージの後に入れる。
- BreadcrumbList: 記事のページで「トップ › Now › 記事の題」を出す。各要素に position・name・item (正のホストの絶対 URL) を持たせる。PBI-0024 のマージの後に入れる。

### ページと metadata

- 404: サイトの見た目の 404 ページを作る。タブ付きの枠の中に「ページが見つかりません」と、トップ・/now・/works への導線を置く。文言は画面の文言の辞書 (ja が正本、en は同じ型) に足す。色はトークンと既存のガラス調の部品だけで作る。ステータスは 404。
  - 404 の metadata は、ルートのレイアウトから受け継ぐトップの canonical・og:url・description を打ち消し、canonical も og:url も出さない。title は 1 つだけ。
  - 対象の経路は 2 つ: 存在しない URL と、知らない id の記事の URL (記事のページで「見つからない」になったとき)。どちらでも同じ 404 のページが出る。
- 記事の見出し: 記事の本文の先頭の見出しが記事の題と同じなら、描画でその見出しを落とす。比べるのは、前後の空白を落とし Markdown の記号を外した平文。そのあと、本文の一番浅い見出しを h2 に寄せ、飛んだ段を詰めて描く。判定は本文の書き方に頼らず、描画側で行う (投稿は API から来るので、書き方の決まりは守られる保証が無い)。PBI-0024 のマージの後に入れる。
- 記事の抜粋: 題と同じ先頭の見出しは、抜粋を使うすべての所 (記事のページの description・BlogPosting・RSS・/now の一覧のカード) で除く。題を受け取る抜粋の関数を 1 つにまとめる。記事の description は、切ったときの「…」まで含めて 120 文字以内にする。
- description: 固定のページの description を 50〜120 文字に書き直す。案は実装の担当が作り、PBI の承認のときに持ち主が確かめて直す。ja が正本で、en も同じ項目を揃える。長さの範囲を当てるのは ja だけ。トップの title (サイト名) は変えない。
- og: og:image と twitter:image を、画像の版が分かる URL (ハッシュ付き) にする。この絶対 URL は 1 か所で作り、og:image・twitter:image・BlogPosting の既定の image がそれを使う。Next.js 16 では子の段の openGraph が親を丸ごと置き換え、ファイルで置いた OG 画像はその段にしか効かないので、作り方は実装の PBI で同梱のドキュメントを読んで決める。og:locale は ja_JP に固定する (クローラは表示言語の Cookie を送らないので、言語に合わせても検索には効かない)。版は、画像の描き方を変えたら上げる定数をクエリに付けて表す。
- 見出し: /career と /works で段を飛ばしている見出しを、h1 の次が h2 になるように揃える。
- 道具のページ: タブの並びの定義に「索引に載せない」の印を持たせ、/theme に付ける。sitemap はこの印の付いたページを載せず、metadata はこの印の付いたページに noindex を付ける。テストの期待値も同じ印から作る。/chat は残す。
- セキュリティヘッダー: Next.js の設定の headers で、すべての応答 (404 を含む) に `X-Content-Type-Options: nosniff`・`Referrer-Policy: strict-origin-when-cross-origin`・`Content-Security-Policy: frame-ancestors 'none'` を付ける。手元の dev サーバーと本番のビルドのどちらでも効かせるため、配信側 (Vercel) の設定には置かない。CSP の本体 (script-src など) は入れない。

### テスト観点

- テスト観点の正本に「seo」を新しく足し、対象を app の全ページ (トップと /now/[id] を含む) にして必須にする。ページを足すと自動で対象になる。
- 観点を足す理由と範囲は新しい ADR に書く。ADR 0029 の「新しい観点は足さない」の行はこの ADR で置き換え、0029 からも参照を張る。既存の SEO の E2E (@smoke・@api-contract) はそのまま残し、新しい検査は @seo のテストとして別に持つ。

### 監査

- PBI-0027 とこの段が本番に出たあと、持ち主が手元で jev-seo を 1 回当てる。Jev による判定を使う (TypeSafe AI の API キーは持ち主のもの。送るのは公開ページの本文だけ)。
- 出力先 (`--out`) はリポジトリの外にする。監査は毎回、公開ページの本文を含む結果のファイル (audit.json) と要約 (digest.md) を作る。これは受け入れる。レポートは Markdown だけ (`--formats md`) にして、Windows で入れにくい PDF の依存を避ける。リポジトリの直下では動かさない。
- 手順書 (`docs/agents/seo-audit.md`) を、この段の PR に入れる。所見は次の段の PBI の材料にする。jev-seo を CI で回すことはしない。

## Testing Decisions

良いテストは、外から見える振る舞い (描画された HTML・応答のヘッダー・関数の戻り値) だけを確かめ、作りの詳細 (どの部品がどう組み立てたか) には依らない。期待値は、表示データ・画面の文言の辞書・サイトの URL の定数・タブの並びの定義から import して作り、文言や URL を二重に書かない。

### 合意済みの seam

1. **描画された HTML (E2E、Playwright)**: 主になる境目。新しい seo 観点のテストが、app の全ページ (トップと /now/[id] を含む) を確かめる。metadata・構造化データ・見出しは、ページを開いたあとの DOM で見る (Next.js 16 は、ふつうのブラウザには metadata を本文の後ろに流して出すため)。JavaScript を動かさない応答で確かめたい項目だけ、クローラの UA を付けた応答の HTML で見る。

   全ページで確かめること:
   - title が辞書から作った期待値と一致する
   - canonical が自分の正のホストの URL を指す
   - 自サイトの絶対 URL (canonical・og:url・og:image・構造化データの url と `@id`) が、すべて正のホストで始まる
   - h1 が 1 つで、見出しが段を飛ばさない
   - 構造化データが 1 つの script で読め、ルートごとに次の型を持つ
   - og:image (版の分かる URL)・og:locale がある
   - 道具のページ (/theme) は noindex で、ほかのページは noindex でない

   ルートごとに期待する構造化データの型:

   | ルート | 型 |
   | --- | --- |
   | 全ページ (トップ・404・/theme を含む) | WebSite・Person |
   | /overview | 上に加えて ProfilePage (mainEntity は Person の `@id`) |
   | /now/[id] | 上に加えて BlogPosting (headline・datePublished・author・publisher・image) と BreadcrumbList (各要素の position・name・item) |

   - /now/[id] は、テストの中で記事を仕込む。本文は 120 文字を十分に超え、先頭に題と同じ見出しを持ち、`##` から始まる見出しを含むものにする。題と同じ見出しが出ないこと・段が飛ばないこと・description が本体と同じ抜粋の関数で作った期待値と一致し 120 文字以内であることを確かめる。
   - 404: ステータス・canonical と og:url が無いこと・導線の href は、応答の HTML で見る。描画と英語の文言を見るテストだけ、ページを開き、そのテストでだけ 404 の読み込み失敗を意図したエラーとして狭く宣言する。存在しない URL と、知らない id の記事の URL の 2 つで確かめる。
   - セキュリティヘッダー: 固定のページ・/now/[id]・404 の 3 種類の応答で、3 つのヘッダーを確かめる。
   - sitemap: `<loc>` のホストが正のホストと同じことを確かめ、取りに行くときはパスだけを手元のサーバーに当てる (本番には要求を送らない)。200 を確かめるのは、固定のページ (道具のページを除く) と、そのテストが自分で仕込んだ記事 1 件だけ。ほかの記事は、ホストと形 (/now/<id>) だけを見る。既存の @api-contract のテストを広げる。
   - /chat では送信の操作をしない (外部の LLM を呼ばない)。
2. **metadata と構造化データを組み立てる関数 (Vitest)**: Person・WebSite・ProfilePage・BreadcrumbList・BlogPosting の組み立てと `@id` のつながり、題と同じ見出しを落とす判定、見出しの段の詰め方、抜粋 (「…」を含めて 120 文字以内)、description の長さ (ja の辞書の固定のページが 50〜120 文字で、title がページごとに違うこと。en の辞書が同じ項目を持つこと)。
3. **sitemap (Vitest)**: 道具のページ (/theme) が外れること、URL がすべて正のホストであること。

### どこで止まるか

- develop 宛ての PR の CI で止まるのは、seam 2・3 (Vitest) とビルド。PR の時点で止めたい検査は、なるべくこの 2 つに寄せる。
- seam 1 (E2E と、必須の観点の穴の検査) は、手元のコミット前の検査 (`pnpm commit-gate`、`scripts/commit-gate.mjs`・ADR 0009) と、develop へのマージ後の CI で止まる。マージ後の E2E が落ちると、リリース PR が作られない。

### 先例

- E2E: 既存の SEO の E2E (トップの metadata・OGP の画像・robots・sitemap) と、記事のページの E2E (metadata・JSON-LD・JavaScript を動かさない応答)。
- ユニット: 既存の metadata のテスト、記事の構造化データのテスト、sitemap のテスト。

### 直す既存のテスト

- 記事のページの E2E は、JSON-LD の script が 1 つで BlogPosting だけと仮定している。`@graph` の中から型で探す形に直す。
- 記事の構造化データのユニットテストは、BlogPosting を丸ごと比べている。author を `@id` の参照にし、image・publisher を足す形に直す。
- sitemap の E2E とユニットテストは、/theme を含む全ページが載ることを期待している。道具のページの印の付いていないページだけを期待する形に直す (期待値はタブの並びの定義から作り、E2E のページの一覧には写さない)。

### 守ること

- E2E は共通のフィクスチャの `test`・`expect` を使い、観点タグと対象ルートを付ける。
- 外部の判定 (Jev) や jev-seo を CI から呼ばない。

## Out of Scope

- 正のホストと配信の転送の向きを揃えること (PBI-0027)。
- トップのサーバー描画と 3D 背景の軽量化 (PBI-0025 で済み)。
- 表示言語ごとの事前描画 (PBI-0026)。
- 英語版を検索に載せること (URL を言語で分け、hreflang を出す)。表示言語は今までどおり Cookie で切り替える (ADR 0026)。
- 作品ごとのページ (/works/<id>) と、経歴の参画案件を HTML に入れること (どちらも次の段の候補)。
- 記事ごとの画像 (PBI-0024)。
- /now の記事の URL を UUID から読める名前 (slug) にすること。
- トップの title を変えること (サイト名のまま)。
- llms.txt と AI クローラの方針。
- CSP の本体 (script-src など)。
- jev-seo を CI や定期実行で回すこと。有料の DataForSEO (順位・被リンク・キーワード)。
- Bing Webmaster Tools の登録 (やるときは持ち主の操作だけで済む)。Google Search Console は所有権の確認が済んでいる。

## Further Notes

- **ほかの PBI との順序**
  - PBI-0024 (記事の画像): 記事にかかわる部分 (記事の見出し・抜粋・BlogPosting・BreadcrumbList) は、0024 のマージの後に入れる。0024 は記事の描画・抜粋・記事のページを作業中で、同じ箇所を触るため。ほかの部分は先に進める。
  - PBI-0026 (表示言語ごとの事前描画): この段は 0026 を待たない。0026 がページとルートのレイアウトを `app/[locale]/` の下に移す方式になったら、404 を `global-not-found` に移し (スタイル・フォント・テーマ・言語を自分で読み込む)、Person と WebSite の出し先を新しいレイアウトに移す。この段では、どちらもルートのレイアウトの 1 か所だけで出しておき、移すときに機械的に移せるようにする。0026 の WORK にこの申し送りを書く。
  - PBI-0027 (正のホスト): 監査はその後に行う。正のホストが揃うまでは、jev-seo を当てても、ページ単位の検査と Jev・PageSpeed の判定がトップだけになり、結果はほとんど空になる。
- **PBI の分け方の制約**
  - seo 観点を必須で足すと、対象のどれか 1 つのルートに @seo のテストが無いだけで、必須の観点の穴の検査が落ちる。だから、観点を足す PBI では、方針ファイルの seo と ADR と、その時点で既に通る検査 (title・canonical・自サイトの URL のホスト・h1 が 1 つ) を、対象の全ルートに 1 本ずつ、同じコミットで入れる。
  - 残りの検査は、その機能を入れる PBI が自分の分を同じコミットで足す (description の長さは description を書き直す PBI、構造化データは構造化データの PBI、など)。
  - seo の E2E は機能ごとのファイルに分け、同じファイルを複数の PBI が同時に触らないようにする。方針ファイル・カバレッジの表 (生成物)・画面の文言の辞書・ルートのレイアウトを触る PBI は、同じ波に並べない。
- **進め方**: 実装は pbi-orchestration-jev で、PBI を小さく分けて進める。PR は develop 宛ての 1 本。
- **持ち主の作業**: description の案を確かめて直す。PBI-0027 の Vercel の設定を変える。本番に出たあとに jev-seo を手元で 1 回当てる。
- **調べた記録**: jev-seo の中身・リスク・サイトの監査・Next.js 16 の SEO の機能・候補の突き合わせ・批評・仕様のレビューは、設計のセッションの作業ディレクトリ (scratchpad の seo2/) に残した。リポジトリには入れていない。調査メモの一部 (トップのサーバー描画・3D 背景) は PBI-0025 のマージで古くなっているので、PBI を起こすときはこの仕様とコードを根拠にする。
