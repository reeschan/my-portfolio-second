PR は「レビューする人が、PBI と差分だけで判断できる」状態で出す。
リポジトリ固有の手順 (`AGENTS.md`、`docs/agents/development-flow.md`) があればそれを正とする。

## 1. 出す前に確かめる

1. 今のブランチが既定ブランチ (`main` など) でないこと。既定ブランチなら作業ブランチを切ってから続ける
2. 作業ツリーがきれいなこと (`git status`)。コミットしていない変更があれば、コミットするか依頼者に確認する
   - コミット前の検査 (例: `commit-gate` スキル、`pnpm commit-gate`) があるリポジトリでは、それを通してからコミットする
3. 対応する PBI (`docs/pbi/<番号>-<slug>/PBI.md`) があること。無ければ `start-pbi` スキルで起こす
   - PBI の受け入れ条件がすべて満たされているか、WORK.md と突き合わせる。満たしていないものは PR 本文の「残っていること」に書く
4. リポジトリが用意している確認を手元で回し、結果を控える
   - 例: lint / 型チェック / ユニット / ビルド / E2E。`package.json` の scripts や CI の定義 (`.github/workflows/`) から拾う
   - 落ちたまま PR を出さない。直せないものは理由を本文に書く

## 2. 本文を組み立てる

PR テンプレート (`.github/pull_request_template.md`、`.github/PULL_REQUEST_TEMPLATE.md`、`docs/PULL_REQUEST_TEMPLATE.md`) があれば、その見出しと順番に沿って埋める。
テンプレートが無ければ次の構成にする。

- **概要**: 何を・なぜ (PBI の目的を 2〜3 行で)
- **関連**: PBI / WORK / ADR へのリンク。Issue があれば `Closes #番号`
- **変更内容**: 利用者から見た変化と、内部の変化を分けて箇条書き
- **設計判断**: 追加・変更した ADR と、その要点
- **テスト**: 足したテスト (ファイルと観点) と、実行したコマンドと結果
- **残っていること / 確認してほしいこと**

書き方:

- タイトルは変更の要約を 1 行で。リポジトリにコミットの型 (`feat:` `test:` など) があれば合わせる
- 秘密情報・個人情報・社内のホスト名を書かない
- 差分にない作業を「やった」と書かない

## 3. 作る

1. ブランチを push する: `git push -u origin <ブランチ>`。ネットワークで失敗したら間隔を空けて数回まで再試行する
2. PR を作る。使えるものを上から順に使う
   - GitHub の MCP ツール (`create_pull_request`)
   - `gh pr create --title ... --body-file ...`
3. 作った PR の URL を依頼者に伝える。続けて CI の結果やレビューを見守るかを尋ねる

## やらないこと

- 頼まれていないのに PR を作らない (このスキルは依頼があったときだけ使う)
- 既定ブランチへの直接 push、force push、レビューの承認・マージ
